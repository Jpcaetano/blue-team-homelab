# Alert Analysis

## Project 03 - Wazuh SIEM and Endpoint Log Monitoring

This document summarizes the alert analysis performed during Project 03 of the Blue Team Home Lab. The goal of this phase was to review selected Wazuh alerts and document them from a basic SOC/SIEM triage perspective.

The analysis focuses on five alert categories:

- Windows authentication failure
- Windows File Integrity Monitoring (FIM)
- Kali Linux sudo activity
- pfSense syslog forwarding
- Snort IDS alert forwarded through pfSense syslog

All events were generated and reviewed inside an isolated lab environment.

## 1. Windows Failed Logon Alert

### Event Overview

| Field | Value |
|---|---|
| Agent | `Win11JOAO` |
| Agent ID | `001` |
| Agent IP | `192.168.6.12` |
| Location | `EventChannel` |
| Decoder | `windows_eventchannel` |
| Rule ID | `60122` |
| Rule Level | `5` |
| Rule Description | `Logon Failure - Unknown user or bad password` |
| Rule Groups | `windows, windows_security, authentication_failed` |
| Windows Event ID | `4625` |
| Event Channel | `Security` |
| Severity Value | `AUDIT_FAILURE` |
| Logon Type | `2` |
| Source IP | `127.0.0.1` |
| Authentication Package | `Negotiate` |
| Status | `0xc000006d` |
| Substatus | `0xc0000380` |

### Analysis

This alert represents a failed authentication attempt on the monitored Windows 11 endpoint. The event was collected from the Windows Security Event Channel and processed by the Wazuh `windows_eventchannel` decoder.

The Windows Event ID `4625` indicates a failed logon attempt. Wazuh classified this event as `authentication_failed` with rule ID `60122` and level `5`.

In this lab, the failed logon was generated as a controlled event. In a production SOC workflow, this alert would require validation of the affected account, logon type, source IP, frequency of failures, and whether there were related successful logons shortly before or after the failure.

### Analyst Triage Notes

- Confirm whether the failed logon was expected or authorized.
- Review repeated failures from the same source.
- Correlate with successful logon events from the same user or host.
- Check whether the event is local, remote, or service-related based on logon type.
- Escalate if repeated failures suggest brute-force activity or unauthorized access attempts.

## 2. File Integrity Monitoring Alert

### Event Overview

| Agent IP | `192.168.6.12` |
| Location | `syscheck` |

| Rule ID | `550` |
| Rule Level | `7` |
| Rule Description | `Integrity checksum changed.` |
| Rule Groups | `ossec, syscheck, syscheck_entry_modified, syscheck_file` |
| FIM Event | `modified` |
| Monitored Path | `c:\wazuh-fim-lab\test-file.txt` |
| Scan Mode | `scheduled` |
| Changed Attributes | `size, mtime, md5, sha1, sha256` |
| Size Before | `0` |
| Size After | `59` |
| MD5 Before | `d41d8cd98f00b204e9800998ecf8427e` |
| MD5 After | `dbb3137ad5913f5791030fd8b9153e11` |
| SHA256 Before | `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` |
| SHA256 After | `c4f878c2aa8e47cbac6efd08531143733e33fe8e136b00f89cd90fb69f0a985f` |

### Analysis

This alert was generated by Wazuh File Integrity Monitoring when the monitored file `C:\Wazuh-FIM-Lab\test-file.txt` was modified. Wazuh detected that the file checksum changed and classified the event with rule ID `550`, level `7`.

The alert shows that the file size changed from `0` to `59` bytes and that multiple integrity attributes changed, including `size`, `mtime`, `md5`, `sha1`, and `sha256`. The JSON also included the content diff generated during the lab test.

This confirms that FIM was correctly configured on the Windows endpoint and that Wazuh was able to detect file modification activity inside the monitored lab directory.

### Analyst Triage Notes

- Confirm whether the file modification was authorized.
- Review the monitored path and determine whether the file is sensitive.
- Compare old and new hashes to validate the change.
- Review the diff when available.
- Correlate with user activity, process execution, and authentication events around the same timestamp.
- Escalate if the file is part of a sensitive directory, startup path, application configuration, or security control.

## 3. Kali Sudo Activity Alert

### Event Overview

| Field | Value |
|---|---|
| Agent | `Kali` |
| Agent ID | `002` |
| Agent IP | `192.168.6.183` |
| Location | `journald` |
| Decoder | `sudo` |
| Rule ID | `5402` |
| Rule Level | `3` |
| Rule Description | `Successful sudo to ROOT executed.` |
| Rule Groups | `syslog, sudo` |
| Source User | `kali` |
| Destination User | `root` |
| TTY | `pts/0` |
| Working Directory | `/home/kali` |
| Command | `/usr/bin/nmap -sS 172.30.2.101` |
| MITRE Technique | `Sudo and Sudo Caching` |
| MITRE ID | `T1548.003` |

### Analysis

This alert represents successful privilege elevation using `sudo` on the Kali Linux endpoint. The event was collected from `journald`, decoded as a sudo event, and classified by Wazuh with rule ID `5402`, level `3`.

The command captured in the event was:

```text
/usr/bin/nmap -sS 172.30.2.101
```

In this lab, the sudo activity was expected and was used to generate controlled network activity against Metasploitable2 using Nmap. This alert demonstrates endpoint-side visibility into administrative command execution on Kali.

### Analyst Triage Notes

- Confirm that the sudo command was expected and authorized.
- Review the source user, destination user, TTY, command, and working directory.
- Correlate sudo execution with network activity, authentication events, and change windows.
- Escalate if sudo usage is unexpected, repeated, or associated with suspicious commands.

## 4. pfSense Syslog Event

### Event Overview

| Field | Value |
|---|---|
| Source Device / Location | `172.30.2.1` |
| Wazuh Agent | `wazuh` |
| Wazuh Agent ID | `000` |
| Rule ID | `100301` |
| Rule Level | `3` |
| Rule Description | `pfSese syslog message received from system log rotation activity` |
| Rule Groups | `pfsense, syslog, lab_validation` |
| Full Log | `May 15 13:56:00 /usr/sbin/cron[95544]: (root) CMD (/usr/sbin/newsyslog)` |

### Analysis

This event confirms that pfSense syslog messages were received by the Wazuh Manager through UDP port `514` and promoted into searchable Wazuh events using a local custom rule.

The event source location was `172.30.2.1`, which corresponds to the pfSense LAN interface. The full log shows a pfSense system log rotation activity generated by `newsyslog`.

This validates the external log source integration path:

```text
pfSense -> Syslog UDP/514 -> Wazuh Server -> Wazuh Event
```

### Analyst Triage Notes

- Confirm that the source device is expected.
- Validate whether the syslog message is normal operational activity.
- Review custom rule IDs and naming for consistency.
- Use this event as proof that firewall/network device telemetry is reaching the SIEM.
- Expand rules and decoders in future work for more detailed pfSense parsing.

### Note

The uploaded JSON contains the rule description as `pfSese syslog message received from system log rotation activity`. This appears to be a typo in the local Wazuh rule description. The intended label should likely be `pfSense syslog message received from system log rotation activity`.

## 5. Snort IDS Alert

### Event Overview

| Field | Value |
|---|---|
| Source Device / Location | `172.30.2.1` |
| Wazuh Agent | `wazuh` |
| Wazuh Agent ID | `000` |
| Rule ID | `100310` |
| Rule Level | `7` |
| Rule Description | `Snort IDS alert: controlled Kali to Metasploitable2 TCP traffic detected` |
| Rule Groups | `pfsense, syslog, lab_validation` |
| Full Log | `May 15 13:41:43 snort[74273]: [1:1000005:1] LAB TCP Traffic from Kali to Metasploitable2 {TCP} 172.30.2.100:38960 -> 172.30.2.101:2040` |

### Analysis

This alert represents controlled TCP traffic from Kali Linux to Metasploitable2 detected by Snort on pfSense and forwarded to Wazuh through syslog.

The Snort alert contains the custom Snort signature ID `1000005` and the message:

```text
LAB TCP Traffic from Kali to Metasploitable2
```

The full log shows traffic from Kali `172.30.2.100` to Metasploitable2 `172.30.2.101`. Wazuh matched the syslog message using a local rule and generated rule ID `100310` with level `7`.

This is one of the strongest results in the project because it demonstrates network-based detection flowing into the SIEM:

```text
Kali -> Metasploitable2 -> pfSense/Snort detection -> Syslog -> Wazuh alert
```

### Analyst Triage Notes

- Confirm whether the traffic was expected or authorized.
- Identify the source host and destination host.
- Review the destination port and service.
- Correlate with endpoint logs from Kali and any related pfSense firewall logs.
- Escalate if this traffic is unexpected, repeated, or associated with suspicious scanning behavior.
- In production, determine whether the source host should be isolated, blocked, or investigated further.

## Cross-Alert Correlation

The selected events demonstrate multiple telemetry sources feeding into Wazuh:

| Telemetry Source | Example Event | Security Value |
|---|---|---|
| Windows endpoint logs | Failed logon | Authentication monitoring |
| Wazuh FIM / Syscheck | File checksum change | File integrity monitoring |
| Linux endpoint logs | Sudo command execution | Administrative activity tracking |
| pfSense syslog | System log activity | Network device log ingestion |
| Snort IDS via pfSense | Kali-to-Metasploitable2 TCP alert | Network-based detection |

These alerts show the difference between endpoint telemetry and network telemetry:

- Windows and Kali agents provided endpoint visibility.
- FIM provided file integrity monitoring on the Windows endpoint.
- pfSense syslog provided network device log forwarding.
- Snort provided IDS visibility for controlled lab traffic.

---

## Triage Workflow Used

The following basic triage workflow was applied to each event:

1. Identify the affected asset or source device.
2. Review the Wazuh rule ID, level, description, and groups.
3. Check the event source, decoder, and location.
4. Review the raw log or event-specific fields.
5. Determine whether the event was expected in the lab context.
6. Describe the expected analyst response in a production environment.
7. Preserve JSON evidence for reproducibility and deeper technical review.

---

## Conclusion

This alert analysis phase confirms that the Wazuh SIEM lab was able to collect, classify, and display security-relevant events from multiple sources:

- Windows endpoint authentication logs
- Windows File Integrity Monitoring alerts
- Kali Linux sudo activity
- pfSense syslog messages
- Snort IDS alerts forwarded through pfSense syslog

The analysis also demonstrates a practical SIEM workflow: generating controlled events, validating log ingestion, reviewing alert metadata, interpreting severity, and documenting expected analyst actions.

All events were generated in an isolated lab environment using owned virtual machines and controlled test activity.
